# SDKWork Agents Kubernetes Deployment

This directory deploys the application ingress and task worker as independently scalable processes from the same immutable SDKWork Agents image. PostgreSQL is the sole scheduling authority; no queue or cache is required for correctness.

Build the image from the SDKWORK checkout root so canonical sibling source dependencies remain available:

```bash
docker build -f sdkwork-agents/deployments/docker/Dockerfile -t registry.sdkwork.com/apps/sdkwork-agents:0.1.0 .
```

## Release Inputs

Before applying a production bundle:

1. Pin both Deployment image fields to the same signed OCI digest produced by the selected SDKWork release. A mutable tag is not a release identity.
2. Provide the externally managed `sdkwork-agents-secrets` Secret. It must contain the production PostgreSQL and IAM/runtime credentials required by the selected `cloud.production` profile. Secrets must not be committed or generated by this kustomization.
3. Review `agents-configmap.yaml` and select the intended source profile. Production uses `cloud.production`; non-production namespaces must use the matching reviewed profile from `etc/topology/`.
4. Apply database migrations as a separate, successful release phase before rolling out either Deployment.

Build and inspect the rendered resources with:

```bash
kubectl kustomize deployments/kubernetes
kubectl apply --server-side --dry-run=server -k deployments/kubernetes
```

## Runtime Contract

- The gateway and Worker both receive Pod UID as `SDKWORK_NODE_INSTANCE_ID`.
  Database bootstrap acquires a PostgreSQL-backed Snowflake node lease for that
  process identity; readiness fails closed if a unique node cannot be leased.
- `SDKWORK_AGENTS_TASK_WORKER_ID` is derived from Pod name and UID and identifies
  scheduler lease ownership. It is distinct from the Snowflake node identity;
  neither value is a substitute for the other.
- Gateway and Worker replica counts, HPAs, PDBs, resources, rollout and rollback
  are independent. PostgreSQL remains the only scheduling correctness authority.
- Worker shutdown removes readiness immediately and drains for up to 150
  seconds; the Pod grace period is 180 seconds. Work that outlives the lease is
  recovered by another Worker with a higher fencing token. Operators must not
  rewrite or delete leases during scale-down or rollback.
- Gateway and Worker each expose `/healthz`, `/readyz`, and `/metrics` on their
  own internal Service. The Worker's bounded PostgreSQL scheduling snapshot runs
  every 60 seconds by default through
  `SDKWORK_AGENTS_TASK_METRICS_SNAPSHOT_INTERVAL_SECONDS`; cardinality backlog
  gauges saturate at 100,000.
- HPA resource signals are a baseline. Production platforms may add a bounded
  pending-Run custom metric without changing scheduling correctness.
- Rollback redeploys the previous signed image digest and matching configuration.
  Database migration rollback or forward-fix follows the reviewed migration
  plan; restored Workers recover expired leases through the normal fenced path.
