## 问题诊断

**报错链路**：`ChatService.ensureChatAgent`（PC 端聊天流程）在每次聊天/会话加载前，若用户选择的模型与 `agent.chat.default` 存储的模型不一致，就会发起 `PATCH /app/v3/api/ai/agents/agent.chat.default`（`agents.update`）来同步模型。后端 API 契约（`agents-app-api.openapi.yaml` 的 `x-sdkwork-permission: ai.agents.manage`，及 `SELF_SERVICE_POLICY_ACTIONS` 有意将 agent update 排除在自助操作外）明确规定更新 agent 必须持有 `ai.agents.manage`。普通聊天用户只持有 `ai.agents.use` / `ai.agents.read`，因此每次模型不一致的聊天都会触发必然的 403 `iam.permission.missing:ai.agents.manage`。

**现状**：客户端已在 `ensureChatAgent` 中 try/catch 该错误（聊天本身不受影响），但 403 请求仍会发起并告警，即用户看到的报错。测试 `chat-resilience.test.ts` 也固化了"尝试同步 + 容忍拒绝"的行为。

**关键事实**：聊天本身完全不需要该同步 —— `sendMessage` 每次按消息传 `requestedModelId`（`AgentChatService.sendMessage` → `resolveChatRuntimeModel`），agent 存储的 model 仅是默认值；且该 PATCH 对共享记录做 last-writer-wins 变更，设计上就不该由普通用户发起。

## 修复方案（客户端按权限门控，不动后端安全契约）

在 `ensureChatAgent` 中，仅当调用方会话的 IAM 权限范围授予 agent 管理权限时才尝试同步模型；否则完全跳过（不发请求、不报错）。授权用户行为保持不变；非授权用户不再产生 403。

### 改动文件

1. **`apps/sdkwork-agents-pc/packages/sdkwork-agents-pc-chat/src/services/ChatService.ts`**
   - 新增纯函数 `callerScopeGrantsAgentManage(scopes: string[]): boolean`，镜像后端 `entry_grants_permission` 逻辑：命中 `ai.agents.manage`、`ai.*` 或 `*` 即放行。
   - 新增可注入的权限范围读取钩子 `configureChatAgentPermissionScopeReader(reader)`（模块级，与现有 `configureChatAgentPort` 风格一致）；默认 reader 从 `@sdkwork/agents-pc-core/session` 的 `createSdkworkChatRequestContext()` 读取 `permissionScope`（pc-chat 已依赖 pc-core，`./session` 子路径已导出）。
   - `ensureChatAgent` 中：`if (model && current.model !== model)` 分支再叠加权限判断；保留原有 try/catch 容忍（应对 scope 声明过期等边缘情况，此时仍不阻塞聊天）。

2. **`apps/sdkwork-agents-pc/packages/sdkwork-agents-pc-chat/src/index.ts`** — 导出新钩子。

3. **`apps/sdkwork-agents-pc/tests/chat-resilience.test.ts`** — 更新两个用例以匹配新契约：
   - 用例 1 改为：无 `ai.agents.manage` 时**不尝试**同步（`updateAttempted === false`）且会话历史正常加载。
   - 用例 2 保留：持有 `ai.agents.manage` 时仍尝试同步。
   - 新增：`ai.*` 通配符放行、匹配函数单测。

### 明确不做的方案
- **后端放宽权限**：`SELF_SERVICE_POLICY_ACTIONS` 注释明确"intentionally exact"，属安全/API 契约变更，需人工评审，不采纳。
- **完全移除同步**：会丢失授权用户的模型同步（现有测试 2 的意图），不采纳。
