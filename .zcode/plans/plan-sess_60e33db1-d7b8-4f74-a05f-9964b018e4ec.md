# 聊天对接 cloudrouter 账号池路由 —— 最终方案

## 核心结论（探索确认）

- **cloudrouter 已完整具备账号池路由体系**：`POST /v1/chat/completions`（OpenAI 兼容）+ 供应商/账号/分组/资源/路由策略/健康/配额/决策日志表 + 账号路由链路（api key → 默认分组 → 策略 → 供应商）+ `Default` 分组约定 + Rust SDK（`cloudrouter-open-sdk`，生成完整、可 path 依赖）
- **agents 不在本地实现路由**：仅调用 cloudrouter Rust SDK，透传用户 auth token
- **唯一缺口**：cloudrouter open-api 目前**只支持 api key**（Bearer 凭证一律按 key 哈希查 `iam_gateway_api_key`），无 authtoken 模式、无 sk-/sp- 前缀判定 —— 需要框架层公共组件补齐

## 改动分布（3 个仓库，无新表、无新路由算法）

### 1. sdkwork-web-framework —— 框架公共组件（高内聚低耦合、可扩展可覆盖）

在 `sdkwork-web-core/src/open_api_auth.rs` 新增 **OpenAPI Bearer 凭证双通道解析组件**：

- `OpenApiCredentialKind { ApiKey, AuthToken }`
- trait `OpenApiBearerCredentialClassifier { classify(&str) -> OpenApiCredentialKind }` —— **可扩展/覆盖**；默认实现 `PrefixedOpenApiBearerCredentialClassifier`：`sk-`/`sp-` 前缀 → ApiKey，否则 → AuthToken（前缀表可注入配置）
- `WebRequestContextResolver` trait 新增 `resolve_bearer_auth_token(&str)`（默认不可用，**可覆盖**）——AuthToken 通道解析身份
- 新增 `resolve_open_api_bearer_flexible()`：单一 Bearer 凭证 → classifier 分流 → ApiKey 通道（`resolve_api_key`）/ AuthToken 通道（`resolve_bearer_auth_token`）
- `RouteAuth` 新增 `OpenApiBearerFlexible` 变体 + interceptors 分支 + web-build manifest 映射（`"open-api-bearer-flexible"`）
- sdkwork-iam-web-adapter：`IamWebRequestContextResolver` 实现 `resolve_bearer_auth_token`（复用现有 IAM bearer/session 解析）

### 2. sdkwork-cloudrouter —— open-api 接入

- `/v1/chat/completions` 认证改造（`openai_chat.rs`/`cloudrouter-http auth.rs`）：Bearer 凭证先经框架 classifier（依赖 sdkwork-web-core）分流——`sk-`/`sp-` → 现有 `ApiKeyAuthenticator`（查 `iam_gateway_api_key`）；否则 → AuthToken 通道（IAM 解析用户身份）→ 映射租户默认账号分组 → 走既有 `resolve_openai_upstream_route_plan` 路由链路（**路由算法零改动**，全复用）
- `sp-` 前缀约定：默认前缀表 `["sk-", "sp-"]`（可配置扩展）

### 3. sdkwork-agents —— 对接调用

- 根 `Cargo.toml`：新增 `cloudrouter-open-sdk` path 依赖（`../sdkwork-cloudrouter/sdks/cloudrouter-open-sdk/cloudrouter-open-sdk-rust/generated/server-openapi`）
- 新 `CloudRouterTurnExecutor`（或 `RuntimeFacadeTurnExecutor` 增加 cloudrouter 路径）：
  - 从 `WebRequestContext`（agents handler 已有该 Extension）取原始 auth token
  - `SdkworkAiClient::new(cloudrouter_base_url).set_auth_token(token)` → `chat().create(OpenAiChatCompletionRequest { model, messages })`
  - cloudrouter base_url 配置化（env `SDKWORK_AGENTS_CLOUDROUTER_BASE_URL`，默认平台 3900 代理）
  - 响应 → assistant_output item（复用现有 turn 持久化链路）
- 会话历史 → OpenAI messages 映射；model id 直传（cloudrouter 模型映射规则处理）
- 前端：移除 `ensureSessionChatRuntime` 的强制 binding 创建（聊天直接走 turn → cloudrouter 路由，免 api key）；旧会话有 binding 仍走本地引擎链（兼容）

## 性能与维护

- **性能**：路由/熔断/健康/缓存全部复用 cloudrouter 既有实现（账号组选择在 gateway 内完成）；agents 侧仅 HTTP 调用，无状态
- **维护**：无新表/无新路由代码；框架组件集中在 `open_api_auth.rs` 单点；认证策略变化只改 classifier/resolver 注入

## 测试与验证

- **框架**：classifier 单测（sk-/sp-/非前缀分流）、`resolve_open_api_bearer_flexible` 双通道、自定义 classifier 覆盖、RouteAuth 新变体拦截
- **cloudrouter**：chat completions 认证分流契约测试（sk- key → 路由；auth token → 身份 → 默认分组）
- **agents**：turns 集成测试（auth token 透传、消息映射、响应转 item）+ 现有回归（cargo test / typecheck）
- 各仓库 `cargo check/test`

## 边界说明

- 不改 cloudrouter 路由算法与账号体系（全复用）
- 上游 CLI 型引擎（codex 等）继续走 agents 本地引擎链（cloudrouter 路径优先服务 account_credential 型/rig 与 openai-compatible 供应商）；如需全部迁移，后续迭代
- 若实现中发现 auth token 与 cloudrouter 内部身份/分组映射需要 cloudrouter 侧新代码，改动局限于 cloudrouter 的认证接入层（不改路由内核）
